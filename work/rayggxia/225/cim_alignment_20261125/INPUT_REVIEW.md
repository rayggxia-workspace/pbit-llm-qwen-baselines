# 当前 FFN TLM 与 RTL 的对齐清单

日期：2026-11-25。结论：**保留现有 TLM 的五核调度与存储架构，补齐关键硬件合同和可核对的事件记录。不是把单核功能原型的串行等待反过来设成整机限制。**

本次为本地源码审阅及建议，没有修改或重跑主TLM、没有新增电路/PPA/模型推理结果。新CIM默认对应5核、250MHz、单核8KiB/16bank。已核对文件及SHA见同目录TLM_RTL_ALIGNMENT_SOURCES_20261125.json。远端PR实时状态未在本次重新确认。

## 2. 已经明确的调度：不要重新发明

`process_28nm/cim_bank32_20261124/actor.py`中：

- `tasks`分发逻辑tile，每个核的loader只向自己的CIM装载。
- `expected[out]`确保同一输出组按K顺序执行，`occupied`防止同组并发更新。
- `owners[state_slot(out)]`防止不同输出组覆盖同一部分和存储位置。
- `credits[core] < 2`限制每核尚未回收的结果资源。
- `retire`及`state_worker`负责共享累加，计算核和累加端可以重叠。
- 正常结束检查任务覆盖、队列排空、信用归零、CIM释放。

**纠正此前RTL建议：**“同一输出组固定给一个核”是另一种可选实现，不是本TLM的既定规则。当前应优先实现TLM已有的共享状态和跨核顺序提交。五核也不是五次重复执行完整FFN。

## 3. 最优先完善的四项

### A. 结果捕获与CIM释放必须分清

当前TLM在计算服务结束后，将结果标识加入retire并释放CIM；之后共享累加端再处理。它已经通过两个信用限制在途数量，并不是无限结果队列。但模型没有在此处展开128路数值结果如何被实体缓冲接收。

建议定义事件：

`sample_last → result_valid → result_capture → cim_release → state_commit`。

- 只有结果被独立缓冲接收，才能释放CIM。如果没有可用槽，计算核停在结果保持状态。
- 若现有服务18/34拍已经包含计数排空和结果捕获，就明确“已包含”，不再额外增加同一拍。
- 若缓冲分拍写入，就按实际写口计算捕获时间；若128列结果并行锁存，也允许一次捕获，但要说明对应的并行寄存器/连线。
- 明确两个槽的位置、位宽和占用周期，并在现有计数/结果寄存器账本中找归属，避免重复计价。

容量示例（仅用于核对接口，不是新增面积结果）：按当前RTL的128×21bit局部计数，五核各两份原始结果的净数据量为3360B；若按128×32bit存储，则是5120B，均另有指数和标签。TLM的每输出组1024B跨K状态是128×64bit，属于另一类存储，不能混为同一缓冲。

当前单核RTL在最后部分和被接收后才释放权重；应通过实体结果槽实现TLM原有重叠，而不是把这个更晚的释放点强加给TLM。

### B. 共享累加的端口与服务边界

现有state worker在非首K块读1024B状态，执行128项跨K更新；非末块写回1024B，末块进入编码或BF16输出。状态端口已有占用时间，不是完全没有带宽限制。

需要补明确：

1. 局部结果是21bit还是扩展32bit进入接口；跨K累加结果是64bit。
2. 每拍接受多少项，计算延迟和启动间隔分别是多少，是否可与下一块状态读取重叠。
3. result slot何时释放、state owner何时释放。释放结果槽和允许下一K更新是不同事件。
4. 状态读写、结果发送、对齐累加及末端编码分别已经包含在哪个服务/动作价格中。

原RTL每拍提交32项，128项最多四次传输。对TLM应先核对这四次传输是否已包含在当前state32服务内，不能看到RTL有四拍就机械再加四拍。

### C. 输入码、尺度和缓存复用按TLM对齐

TLM对GU输入码读取80B；对Wd非线性输入码读取128B并另外读尺度；权重尺度另外读取。每核缓存当前K块，`input_key`命中时不重复加载输入码。

本轮RTL的96B元数据记录和六次16B读取，是为复用旧数值fixture建立的功能接口，尚未实现上述数据布局及复用策略。因此：

- 保留TLM的复用，不把每tile读96B强制设成整机事务。
- 补一个明确的布局表：输入码、输入尺度、Wg/Wu/Wd尺度、g/u编码分别在哪里，记录宽度和失效条件是什么。
- 核内缓存必须计入存储；优先复用本来就必须保持的输入码寄存器，不额外复制同一内容。
- 缓存key至少在当前layer/命令/模式生命周期内有效；现actor阶段内只记K是有上下文前提的，RTL不能跨命令沿用旧命中。
- 逻辑1B或2B尺度访问需按实际16B物理字及已有缓存/合并策略计费。要检查父BeatSRAM的行为，不能直接断言目前仅按1B收费，也不能未经核对再次向上取整收费。

### D. DMA有限缓冲必须是五核共享资源

TLM已有16KiB返回保持与信用约束，保留此容量。完善全局描述符/包标签/目标core/bank分配，以及满队列时的回压。

- RTL当前单核四路FIFO的总载荷为16KiB，包头元数据另960B。这是实现候选，不意味着五核要复制五份。
- 五核正式实现采用共享容量/信用；按core和bank路由数据，某核不可写时，不应无条件阻塞所有无关核。
- 包头和描述符优先归入已有接口账本，查清是否已计，不把960B直接当成额外缺失总量。
- 定义何时预留返回空间、何时返还信用；返回空间不足时暂停上游请求。
- 不要求增加整个8KiB普通SRAM中转块。CIM仍直接接收DMA返回。

本次未恢复并审阅父版本全部DMA/BeatSRAM源码，因此以上是需核对的实现合同，不是已证实DMA模型存在错误。

## 4. 随机状态：补接口，不把随机源改成新的瓶颈

TLM目前计入GU每采样1个共享R8字、后级每采样3个共享R8字等动作，但不生成逐元素随机数。它无需为整机计时而完整模拟每个PRNG位。

RTL多核需明确逻辑tile身份与随机状态的关系。为保持和当前顺序数值参考逐位一致，应实现tile起始状态分配/跳步，或等价的确定性流划分。不能只用“第一个空闲核的当前种子”然后声称保持原事件序列。

TLM只需增加该接口的启动延迟、可持续供给率及新增动作成本。若复用既有随机前端，保留其价格；不得重复计费。起始状态生成方式尚未实现，当前不将其假定为零开销，也不假定每次要串行推进全部之前的样本。

## 5. 统一周期单位及算子服务合同

actor里同时存在`service['frame_cycles']*10`、`align_time(...,4)`和`delay(40,...)`。父模型可能把历史10ns基准延时转换为当前频率；仅看这些表达式不能认定模型按100MHz执行。

建议保留计算结果的前提下，封装或注释为“当前时钟周期→ns”的统一入口，并测试250MHz下：18拍=72ns、34拍=136ns；状态端口服务与配置一致。冻结父delay实现的来源/SHA。不要仅把源码的10改成4，造成双重缩放。

为GU/Wd、跨K累加、g/u编码、BF16输出分别列出：输入就绪条件、启动间隔、输出延迟、结果捕获宽度、缓冲深度、是否包含SRAM事务。采样数变化只修改确实与采样相关的部分，不缩放所有控制/存储周期。

## 6. 用同一小形状核对，而不是要求所有模块逐门仿真

增加可选小轨迹输出，事件至少包含：layer、mode、out_group、k、core、transaction_id、cycle/ns、bytes、resource、原因。重点核对：

- 每个tile装载8192B，CIM完整且空闲后才运行；同核写算互斥。
- 每个逻辑tile只执行一次；同输出组K顺序正确；末K之后才编码/输出。
- 每核结果信用不超过2；缓冲接受结果前不释放CIM。
- 所有未命中输入码的实际读取、缓存命中和尺度读取均有记录。
- 所有末端完成通知在相关写回/队列排空之后发出。
- 逐项列出等待：权重、输入、结果槽、跨K依赖、状态端口、末端编码，避免只给总周期。

先比较工作量、依赖和资源占用，再比较时间；RTL和TLM允许不同合法仲裁顺序，不能强求所有独立事务完全同序。但相同仲裁模式下应能对齐关键路径。报告应覆盖同资源的一个小FFN、五核压力用例、一个Decoder层。没有验证依据时不先规定“误差小于某百分比就合格”。

## 7. 执行优先级和判断

1. **先补A/B服务合同与结果槽账本**，这决定CIM能否按TLM释放、五核是否真能隐藏搬运。
2. **RTL按C/D实现输入复用与共享DMA**，TLM保留既有优化；仅在发现实际不支持的资源时修改其参数。
3. 实现随机状态分配，补对应成本；统一周期单位和最小轨迹。
4. 用上述同一小形状对齐，再决定是否重跑完整模型。

已有5核单层FFN566.452µs等结果继续保持原版本标记。本次不能给出修改后的新时间、能量或面积，也不能因为发现待明确接口就宣布旧数值全部失效。最可能改变性能结论的是结果捕获/共享累加吞吐，其次是输入缓存和DMA队首阻塞；常规握手不需要全部提升成逐周期整机模拟。

**最终建议：修改TLM的合同、配置入口和可验证性；让RTL追上已有调度，不先削弱TLM的并行能力。**
