# 当前TLM的保守调度：已确认限制、论文对照与修改边界

日期：2026-10-27。负责人：rayggxia。沿用Issue187 / PR189，调度实现仍归Issue186。

**结论：当前模型存在会限制性能的保守调度政策；容量、依赖和计费检查本身应保留。不能概括为“大部分模拟器都不会保守调度”，也不能将当前结果视为真实硬件性能的保守上界。** 已核查的成熟工具通常会表达或搜索流水、预取和资源复用；对不支持的并发仍会顺序执行。应比较具体策略和硬件能力，而非比较检查语句多少。

审计版本为[PR192](https://github.com/rayggxia-workspace/pbit-llm-qwen-baselines/pull/192)的`556462dc5db37582310302ed8b916d717b4d6ceb`，分支`task/186-local-pipeline`。以下当前配置指`clock500_resource_20261026`已封存的12项，不代表所有历史配置，也不代表随后新增RTL已回填TLM。本轮只有源码/配置审计及Scheduler软件微例；没有新完整TLM、GPU、PPL、RTL或EDA实验。

## 1. 防御性检查与保守政策必须分开

| 应保留的正确性检查 | 应作为架构选择验证的调度政策 |
|---|---|
| 容量不越界、槽不被覆盖、代次正确 | 一次仅保留一个待接收宏DMA |
| 输入/权重到齐才消费、结果就绪才写回 | 整个DMA批次排空后才接下一批 |
| 请求响应匹配、字节/样本守恒 | 整个SRAM描述符占用所有涉及bank直到结束 |
| 不向已经推进的DRAM actor插入过去事件 | 按Python调用先后预约所有资源，不回填空闲区间 |
| 不重复计费、未知成本不自动补零 | 跨输出窗口禁止提前编程、数字预填充默认关闭 |

同一条`raise`可能同时维护上述两类条件。应先让资源和生命周期表达合法并发，再更新相应检查；不能直接删检查或关闭`strict_time_order`来制造加速。删除Python检查至多改变模拟器运行耗时，不会自动改变被模拟硬件的时延。

## 2. 已确认的保守限制

下表定位全部针对上述固定提交；“可能高估”不等于已经测得可去除的整机时间。

| 项目 | 当前行为与定位 | 影响判断 | 合理改进及必须保留的成本 |
|---|---|---|---|
| 提交顺序资源预约 | `unified_v6/core.py::Scheduler.reserve`仅保存每资源最后完成时间，按提交顺序取max，没有空隙插入 | 先提交但晚就绪任务可能挡住后提交的早就绪任务；不保证工作保持型调度 | 明确真实FIFO政策，或实现按就绪事件推进的有限队列；保留依赖和公平仲裁 |
| 宏DMA/SG批间排空 | `core.py::DRAM.ranges`为每组调用同步bridge；`dramsys_backend.py::_exchange`等待返回，下一组issue不早于前组done | 批内已有多个在途请求，不能说每burst串行；但跨描述符/批次并发受限 | 异步request/completion或有限描述符队列，计response缓存与credit，保持actor时间单调 |
| SRAM整描述符占用 | `core.py::SRAM.transfer`一次预约涉及bank及`sram_fabric`直到完成 | 字数/bank统计细，但仲裁模型粗；可能阻止其他访问利用空隙，并非优化仲裁 | 根据实际端口和fabric，按beat/短块释放，或用经验证的并发服务宏；不可赋予无限端口 |
| 数字共享预填充默认关闭 | `tile_pipeline.py`中`digital_shared_prefill`默认False；未启用时`fill`要求上一active已退役 | 主要重叠下一块DMA，未充分重叠下一共享填充/本地装载 | 在另一槽容量、读写端口和响应缓存允许时启用；本地第二bank需要额外计费 |
| SC跨窗口编程受限 | `ffn_local_pipeline_20261025/model.py::matrix_local`仅在`nxt[0]==kw`且`nxt[2]==j`时提前program | 相同输出/K窗口可重叠，跨窗口延后；是有意保守政策，不是已证明的物理禁止 | 以部分和、系数、随机context的所有权验证更广重叠，并计额外状态/缓冲 |
| 描述符生成统一一拍/span | `memory_profiles.py`设置`descriptor_span_ns=1e9/core_hz`；生成全部runs后才提交本次访问 | 吞吐值和“先全部生成、后提交”的屏障均未由DMA实现验证 | 连续地址生成与下游发送可流水；用小型控制器或微基准确认，不能直接把成本置零 |
| 固定CDC宏 | `SRAM.transfer`每次传输加`cdc_ns` | 其合理性取决于异步FIFO/握手的接口边界；若实际连续流无需逐项重付，可能过计 | 区分首次可见延迟与后续吞吐，计有限跨域FIFO；不能取消跨域延迟 |
| 桶归约/恢复串行拆分 | TLM有两个时间资源，已有恢复RTL含二者；`clock500_resource_20261026/PPA_METHOD_ZH.md`已披露 | 时间资源与电路边界待对齐，不能认为两个服务时间必然都是必需开销 | 按同一物理宏的latency、II、lane及占用回填；能量当前已只收一次，不再扣第二遍 |

这不是最优调度证明。某些限制若正是最终硬件的FIFO/单DMA/单端口设计，便是合理模型；需要在论文中说明为何选择该实现及资源取舍。

## 3. 最小实测软件例：调用顺序会影响预约

两个独立任务使用同一端口：A在100ns就绪、执行10ns；B在0ns就绪、执行10ns。

先调用`reserve(A)`再调用`reserve(B)`，当前Scheduler得到：

```text
A：100–110ns
B：110–120ns
```

同一组就绪条件存在合法安排：

```text
B：0–10ns
A：100–110ns
```

软件微例确认120ns与110ns的差别。若真实硬件严格先A后B，这个等待合理；若模拟器调用顺序只是实现细节，则它施加了额外限制。**没有测得此现象在36层模型中的占比，不把10ns或相对差值外推为整机加速。** 复现脚本及源码/结果SHA在`work/rayggxia/187/check_conservative.py`和`CONSERVATIVE_CHECK.json`。

## 4. 数字与SC的保守程度并不对称

回读12个`RESULT_SUMMARY.json`确认：

- 全部未设置`digital_shared_prefill`，按代码默认False处理；BF16参考为case10/11。
- 10个SC情景均设置`local_pipeline.overlap=True`、`weight_bypass=True`。
- SC可绕过部分共享SRAM权重搬运并使用局部双bank；数字参考没有同样启用共享预填充。

这可以代表不同硬件，但目前不能解释为双方在同面积、同精度及各自充分优化后的比较。当前约64.5ms与110ms还包含W8/稀疏Attention/专用资源等差异；不能全归因随机计算。后续应给数字和SC分别优化映射/供数，并记录新增本地bank、端口、缓存与控制成本。

## 5. 功耗方面：部分保守，但整体不是上界

明确的保守处理：恢复开钟占用使用两段时间之和的上界；GU/Wd共享最大B7硬件，未用档位不默认免费关钟。B7功耗按B4和面积比例外推属于代理，**没有保证其误差一定向上**。

与此同时存在可能乐观或尚未定界的项：500MHz全链路未STA、固定门控去除比例80%、本地宽读出与广播实现、HBM/PHY/controller能量、数字2pJ/MAC等代理。因此“有保守限制”不能推出“芯片一定比预测快/省能”。完整PPA仍有unknown，不能将已计价小计称为整机。

新PR196的计数/数字RTL属于后续表征路线，不能据其功能通过改写本次封存结果或宣布已有新PPA。

## 6. 论文/模拟器对照：能确认什么

| 原始来源 | 已核查的机制 | 可以得到的结论与限制 |
|---|---|---|
| [LLMCompass，ISCA2024论文](https://augustning.com/assets/papers/llmcompass-isca-2024.pdf)；[固定代码](https://github.com/PrincetonUniversity/LLMCompass/blob/2e015fd2ee750e6cad8d7152df52551e5b41ef20/software_model/matmul.py) | 搜索分块/循环顺序及双缓冲；特定M=1/N=1 heuristic分支采用计算与外存时间max | 常以优化映射为目标；快捷分支简化片上限制，不是所有路径都无保守约束 |
| [AttAcc固定代码](https://github.com/scale-snu/attacc_simulator/blob/c60005143a6b492d7ef83231723386478b59a506/src/devices.py#L194) | 普通算子计算/访存取max，PIM矩阵请求用Ramulator，系统另做流水/通信 | 算子内部较充分重叠；仍有资源、阶段及模型近似，不能把任意相加改为max |
| [HyperAccel LPU](https://arxiv.org/html/2408.07326v1)的Dataflow/Methodology | 存储、矩阵/向量执行、地址生成并行；权重流式供给 | 并行是其明确硬件设计，需相应通路与端口；绝对时间还依赖HBM3资源和配置 |
| [Kelle，MICRO2025 §6](https://arxiv.org/html/2510.16040v1#S6) | 以运算量/吞吐、字节/带宽分析；数据寿命分析中忽略较小计算项 | 不逐项累加所有小开销；其可忽略条件不能自动移植到我们的随机长采样路径 |
| [ONNXim代码](https://github.com/PSAL-POSTECH/ONNXim)；本项目`unified_v6/SCHEDULER_RESEARCH_ZH.md` | 依据tile状态、有限缓冲与资源就绪执行，支持有条件的搬运/计算重叠 | 有检查和有限队列并不等于过分保守；不能据存在多核/流水就宣称全局最优 |

以上是代表性来源，不是对模拟器总数的统计。**不能写“大部分模拟器不会这样”或“论文一般默认最优”。** 可以写：“已核查工具通常会建模/搜索合法的流水、预取及资源复用；我们额外施加的批间屏障和窗口限制，需要硬件依据或敏感性说明。”

## 7. 下一步建议：验证政策，不删除守恒

1. 先检查真实运行是否出现由预约顺序造成的空洞；事件驱动改进必须保留有限队列与时间单调。
2. 给数字参考验证并启用合理的共享预填充，并评估可行的本地双bank或直达供数；记录资源代价。
3. 单独评估跨宏DMA批次的有限并发；保留每个burst的JEDEC约束和回压。
4. 验证SC跨窗口编程，保持随机重放、系数、部分和与数值顺序合同。
5. 将桶归约/恢复统一映射到真实宏；PPA用准确状态/区间而非任意累加上界。

每次先隔离一个策略，再做组合；比较两侧的时间、字节、峰值缓冲、端口占用及面积/能量代价。当前未量化各项能省多少，不能把潜在收益相加。原阻塞模型保留为特定实现的对照，最终主模型采用有实现依据的政策，不再通过“未知就串行”隐式决定性能。
