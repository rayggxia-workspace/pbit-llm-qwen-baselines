# BF16数字矩阵基线：已有证据、比较预算与补测模块

2026-10-28；接续Issue204及已合并PR205，BF16补充由独立分支交付，准确回执见work/rayggxia/204/bf16_baseline/PUBLICATION.json。负责人rayggxia。读取既有结果与一手文献，不新增EDA、模型推理或PPL，不接管Issue107，不修改其源码、STATUS或旧记录。

目前结论：BF16值得作为另一条数字基线，但现有证据不能证明本OR4架构相对成熟BF16数字核有巨大能耗优势。已有本工艺BF16 RTL时序失败；成熟28nm论文的能耗量级已接近本SC核心。必须把同工艺的有效实现补齐，不能以旧失败实现充当强基线。

## 1. 数值合同

主数字基线采用BF16输入、BF16权重、FP32累加，最后按需要转BF16。Google TPU官方说明采用这一乘法/累加组合，[Arm也提供BF16乘积累加到FP32的指令](https://developer.arm.com/community/arm-community-blogs/b/ai-blog/posts/bfloat16-processing-for-neural-networks-on-armv8_2d00_a)。[Google文档](https://docs.cloud.google.com/tpu/docs/bfloat16)同时明确其BF16次正规数清零等行为；是否支持subnormal、NaN/Inf、RNE、融合或分离舍入都要写入测试合同。不能把每次累加都舍入BF16的低成本结果直接称为此基线。

BF16乘法的有效尾数是8×8位，包含隐藏位；并非16×16位整数乘法。额外成本来自每个乘积的指数、对齐、符号、宽部分和、规格化、舍入及真实流水状态。融合点积可让多个乘积共享部分处理，不能简单按64个完整标量FMA相加来代表最佳点积核。

当前SC是W8、T32、普通OR4、缩位饱和等近似合同，不保留BF16完整动态范围和精度。与BF16比较体现精度/范围/成本的取舍；若要证明随机机制本身有效，仍要保留匹配输入量化、权重、尺度和输出质量的INT8/低位确定性数字控制。

## 2. 可核验的数字

同一“64项点积”作为工作量单位，一次MAC按乘法+加法两次逻辑运算计；不把32拍采样当32份有用点积。

| 对象 | 每64项点积能量 | 面积 | 时间/状态 |
|---|---:|---:|---|
| 本SC bank54，T32 | 69.4633 pJ | 0.00552407 mm²，raw×0.81 | 350 ns / 35拍；前布局计算核 |
| 本SC bank50，T32 | 67.9817 pJ | 0.00544709 mm²，raw×0.81 | 350 ns / 35拍；前布局计算核 |
| 28nm多精度数字PE论文，BF16 | 条件换算72.6691 pJ；按9路补齐72项为81.7527 pJ | 摘要未核验，留空 | 论文1.471GHz slow corner；N64完整延迟未知 |
| 本工艺旧BF16乘积/FP32累加 | 没有合法N64结果 | SS原始0.14396652 mm²，单次×0.81为0.11661288 mm² | SS100MHz setup −26.219376 ns；禁止作有效100MHz基线 |

SC数值来自上一轮33模块能耗库的replay三seed平均；同SS1.08V/125℃/100MHz。bank为预解码7幅值位及乘积符号、abs(W)≤127，不含权重SRAM、概率存储、PRNG/比较器、编码、完整格式恢复、物理广播、CTS/SDF/SPEF等。表中面积为标准单元面积，不是芯片面积。SC与数字旧激励、数据范围和模块边界也未全部对齐。

论文为Li等《A Reconfigurable Processing Element for Multiple-Precision Floating/Fixed-Point HPC》，TCAS-II 71(3)，1401–1405，2024；[香港大学作者机构页面](https://hub.hku.hk/handle/10722/339469)与[IEEE摘要](https://ieeexplore.ieee.org/document/10272667/)可核实28nm、9路BF16、1.471GHz slow corner、1761.41 GFLOPS/W。按2 FLOPs/MAC的常用计数，推算：

`E_MAC = 2000 / 1761.41 = 1.13545 pJ`；`E_dot64 = 64 × E_MAC = 72.6691 pJ`。

这是从摘要能效作出的满利用率换算，不是论文已测的N64事务能量。本轮未获得完整正文，不能核验其全部累加精度、FLOP计数定义、供数、反馈、归约、输出舍入、PVT电压和面积合同。72项补齐只是利用率敏感性示例，不是其真实N64调度。也不按55/28或0.81缩放该论文的能量/时间/面积。因此与69.46pJ接近只说明“不能预设数量级优势”，不构成性能胜负结论。

## 3. 为什么旧本地BF16结果不能直接证明SC优势

旧run `digital-ppa8-20261025-consolidated-review`，KIND2：SS `38374869_1`、TT `38374995_9`均9窗口。SS stream三seed平均1.04933mW；原窗口731个有效项、5个变长输出，不能用“总能量/5”当N64点积成本。SS/TT setup分别−26.219376/−10.537953ns，旧probe功能通过不等于时序可运行。ESTIMATE.json保留逐项输入计费诊断，但不外推为有效N64能量。

源码核查：`nr_stream_accumulator(KIND1)`为BF16补低16个0送入通用FP32乘法，再送`fc_fp_add`、FP32 state；不是专门融合的BF16点积。常量输入可以被综合裁剪，不能仅因实例名FP32就断言保留24×24乘法器。

`fc_fp_add(FRAC23)`用26次依赖式“检测最高位→左移一位→指数减一”组合展开。该写法有形成长串联逻辑的风险；这只是RTL结构诊断，未做新关键路径归因或优化后PPA，不能声称全部面积/延迟均由这一个循环造成。通用`fc_fixed_to_fp`和`fc_scale_mag`另有宽动态移位、32位integer指数/循环控制。更合理的实现应使用平衡LZC、一次桶形规格化、限定指数/移位宽度，融合可共享的处理，并把末项格式转换移出每项反馈环。

原始文件/两份summary均按SHA绑定，见ESTIMATE.json。面积本轮只在派生字段乘0.81；不改旧台账、原报告或波形。

## 4. 能耗和速度门槛

以bank54计算核为起点，数字每MAC成本达到以下数值时，才有对应能量比：

| 数字能量 / SC能量 | 数字阈值pJ/MAC | 数字N64阈值pJ |
|---|---:|---:|
| 1倍，刚好持平 | 1.08536 | 69.4633 |
| 2倍 | 2.17073 | 138.9267 |
| 5倍 | 5.42682 | 347.3167 |
| 10倍 | 10.85365 | 694.6333 |

这不是55nm BF16实测预测区间，而是可证伪预算。BF16若测得2/3/5pJ/MAC，理想64项算术分别128/192/320pJ，相对当前SC计算核为1.84/2.76/4.61倍。SRAM、随机前端、编码和结果恢复必须按两侧真实边界补入；ESTIMATE.json给出SC额外0/10/25/50pJ的条件敏感性，额外成本不是已测值。

速度方面，SC350ns/35拍，对应约1.83个有用MAC/周期的平均处理率。数字基线要比较单lane、小型2/4/8项点积和资源/延迟折中，不能只比较64路全并行的一拍大核。两条MAC算术lane也不保证32拍完成同一输出：FP32反馈依赖、流水填充/排空、部分和归约和转换都必须计入。插流水线也不能自动得到同一累加流II1。

## 5. 后续本工艺补测的最小模块集

建议以经过验证的[FPnew/CVFPU](https://github.com/openhwfoundation/cvfpu)为正确性/结构参考，冻结准确版本、依赖和许可证；不要默认集成所有除法/开方/格式支持，也不要把成熟源码直接视为本工艺已测IP。候选：

1. BF16×BF16精确尾数乘法和指数/符号，输出FP32；正常范围可精确容纳16位乘积有效位，溢出/下溢合同另验。
2. FP32加法：树形LZC、对齐、加减、规格化、RNE，明确subnormal和异常数处理。
3. BF16×BF16+FP32融合MAC，独立于分离乘法/加法；融合与分离在溢出/下溢等情况下不必逐位相同。
4. DOT2/DOT4/DOT8：共享最大指数、乘积对齐、压缩/加法树和末端规格化/舍入。先测小块，再评N64组合，不将64个标量MAC面积直接当最佳点积面积。
5. N64完整帧封装：真实输入/权重保持、合法的部分和上下文、反馈调度、最终归约/转换及CE/时钟。至少一版达到或接近35拍预算；M8共享/连续II再单独验证。

每类先三seed功能/浮点oracle（端点、相消、指数跨度、异常/次正规、first/last/stall），再复用当前SS1.08V/125℃/100MHz和同端口负载做DC/STA/PT；若反馈时序失败则实现真实多周期/交错上下文，不能只加时序例外。功耗测试使用相同数值向量的BF16与SC对应编码，报告各自质量；先分开计算核边界，再闭合存储/随机源/恢复。台账登记真实新run，面积raw×0.81，仅一次。

[Alexandridis等2024论文](https://arxiv.org/html/2408.11997v1)展示28nm BF16阵列可通过简化规格化减少成本，但其中部分和采用16位有效尾数，并非本报告FP32累加主合同；[FPnew硅验证论文](https://arxiv.org/html/2007.01530v1)的22FDX Ariane版本明确不含expanding FMA。因此这些数字不混充55nm BF16×BF16→FP32实测。
