SRAM标定与DRAM低功耗：给PT仿真和事务模型的数据需求
日期：2026-10-14

先看结论

现在最需要补齐的不是“一个SRAM平均功率”，而是下面这张小成本表。
先测真实宏和它的读出保持接口，结果回来后就能替换事务模型中的假设参数。
本文件是仿真任务说明，不代表新SRAM已经完成PT或时序验证。

| 必测项目 | 最后需要给出的结果 | 在事务模型中的作用 |
| 正常读取 | 每次读的动态能量pJ、响应延迟、连续读间隔 | 权重/KV/随机流缓存的读成本和吞吐 |
| 正常写入 | 每次写的动态能量pJ、写周期，分别测全字与实际掩码 | DMA装载、随机流写入、部分和写回 |
| 不访问，时钟仍运行 | 内部/开关/漏电功率，Q是否保持有效 | 采样期间宏的真实待机成本 |
| 不访问，合法门控停止时钟 | 保持功率、重新启用的延迟与能量 | 能否降低长期等待/驻留成本 |
| 预读后持续供给计算 | 一次预读能量、4096拍保持能量、Q稳定性 | 核验“权重不必每拍重读”的架构 |
| 宏和外围面积 | 单宏物理尺寸、宏数量、标准单元面积 | 片上缓存与活动tile的真实面积 |

一、DRAM进入低功耗后，已经算出的整体收益

你的理解成立：当前tile的权重已经在片上，采样时不需要反复访问DRAM。
但并非整个Qwen权重都已常驻SRAM。当前模型是16MiB权重cache、1MiB工作缓存、
8个64×64计算阵列；FFN的24层INT8权重就约299.25MiB，后续tile、其他层、lm_head
以及KV仍需访问DRAM。因此适合在空闲段进入保数据的低功耗状态，再按请求唤醒。
这不是切断DRAM供电，也不是把DRAM功耗记为零。

已有对照：完整24层，batch=1，2K上下文，连续decode两个token取平均，
双通道DDR4；仅将DRAMSys策略从NoPowerDown换为Staggered，其余资源相同。
Staggered实现支持power-down以及随后进入self-refresh的状态管理；
本次不是自定义的“整个FFN期间强制关内存”策略。

| 方案 | 整体能量，不低功耗→低功耗 | 整体节能 | DRAM部分节能 | 时间变化 |
| 固定权重随机FFN | 545.29→470.20 mJ/token | 13.77% | 17.15% | 488.00→488.94 ms，增加0.943ms，即0.193% |
| 双随机Sz FFN | 38.47→26.67 J/token | 30.67% | 34.41% | 45.05612→45.05672 s，增加0.602ms，即0.00134% |
| 数字BF16 | 156.66→171.99 mJ/token | 本配置增加9.78% | 本配置增加10.42% | 增加0.024ms，即0.034% |
| 数字INT8权重FFN | 108.62→119.28 mJ/token | 本配置增加9.81% | 本配置增加10.49% | 减少0.007ms，约0.015% |

对两种随机FFN，本次没有明显增加整体时间，但节能也不是把DRAM这一项全消掉。
数字路径的反向结果提醒我们：短空闲段频繁切换状态不一定划算，且功耗参数会影响判断。
本次采用官方示例电流系数；VPP低功耗电流还需核验，I/O参数也未标定。
以上是模型情景，不是目标芯片实测；8K目前只有NoPowerDown结果，没有8K低功耗对照。
双随机的45秒结果属于现有全局均匀随机字源映射，不能当成原生p-bit的速度上限。

后续控制策略可利用已知采样长度与双缓冲，在下次DMA前提前唤醒DRAM。
一个简单的判断是：
  空闲期间省下的能量 = (正常待机功率 - 低功耗功率) × 空闲时间
  只有它超过进入/退出的额外能量，休眠才划算。
  若退出延迟被预取隐藏，整体延迟几乎不变；否则它会变成等待时间。
具体阈值应来自目标DRAM参数，不能把上述示例百分比直接套到其他DRAM/HBM。

二、先确认真实SRAM库具备什么

PT/PrimeTime PX或对应PrimePower功耗功能，是利用已有库表和活动分析电路，
不是从行为Verilog自动推导SRAM位单元功耗。需要真实宏Liberty/.db中的有效
时序、内部功耗和漏电模型。普通PrimeTime时序许可不等于一定具有功耗分析许可。
若宏只有端口stub、无功耗表，不能把黑盒功耗0当作SRAM收益；应找厂商表征库。
若低功耗模式没有相应模型，需要厂商数据或电路级表征；不能靠PT补出不存在的表。

先提供/核对：
1. 宏名、深度D、字宽W、端口类型（1RW/1R1W等）、掩码粒度、读写控制极性。
2. 同一版本的.lib/.db、功能模型、datasheet；有条件提供LEF、GDS和低功耗说明。
3. corner、电压、温度、time_unit、功耗单位、面积单位及文件SHA256。
4. 时钟到Q、地址/控制/写数据setup/hold、最小周期/脉宽、允许slew和输出负载。
5. CE关闭后Q是保持、清零、X还是三态；停止CLK是否保数据/保Q；唤醒需要几拍。
6. 若有NAP/RET/sleep：阵列数据是否保留，Q是否有效，进入/退出要求和模型覆盖。

第一批建议100MHz、与现有标准单元匹配的SS/1.08V/125°C。
只在SRAM确实提供这个corner时使用；不能用TT SRAM混配SS逻辑而不说明。
TT常温可作为第二批典型值。漏电最坏corner应按库确认，不默认“SS就是漏电最大”。
不要通过修改margin/test模式、虚构false_path/multicycle使100MHz看起来达标。

三、我们的SRAM分成两种用途，不要混为一个宏

| 用途 | 当前需求 | 实际需要测的接口 |
| 大型权重cache/工作缓存 | 默认16MiB权重cache、1MiB工作缓存；64GB/s是当前假设 | 普通banked SRAM的顺序读写、端口冲突、bank选择/互连、待机和面积 |
| 计算旁的权重驻留 | 每个64×64 tile需4096个9位权重，36,864bit=4.5KiB | tile准备、同时向64个输出供给权重、采样时保持、宏时钟策略 |

工作缓存还承载随机字流重放、BF16中间量、部分和和logits。
其中64路×4096拍×12bit的随机字流约384KiB；它会读写，不能套用静态权重保持功率。
概率/符号寄存器按原方案保留，此次SRAM库不会自动取代它们。

本地已有可复用工程：sc_wide_sram100_20261014。
它计划用4个32×144同步宏，同址预读出一组576bit，即64个9位权重；
共保存32组，容量18,432bit=2.25KiB，计算期间CEB=1、CLK仍为100MHz。
目前看到的是脚本和绑定协议，未看到可用的真实生成宏及最终PT结果，不能宣称已验证。
脚本默认lpwr=0，现有包装没有NAP/RET连接；先测正常CE保持，不假设它有深度休眠。

非常重要：这个工程一次供给一个点积输出，不能把其容量/面积当成完整64×64并行tile。
若直接复制成64个同时工作的输出列，则需256个32×144宏，总容量144KiB；
这可存32个tile的权重，并非只有4.5KiB。面积和全部宏的保持功率都要计入。
另一路是普通SRAM分拍预读，再用本地保持单元保存36,864bit；必须计入这些保持单元。
选择哪一路由真实宏端口/字宽/面积决定；不能把“一个普通读端口”当成任意多路并行。

旧sc_weight_storage_or4_20261014中的64词全部同时可见行为模型，不能直接拿来测真实SRAM。
已有宽字工程计算核心是OR4；其存储标定可以参考，整核OR4功耗不能替代当前精确G1核心。

四、第一批PT任务：先做这些，足够开始填模型

先实例化真实宏和必要的控制/ICG/输出保持外围，生成真实活动，再做PT功耗和STA。
对读写项目，先用连续有效请求窗口，避免把大量空闲时间混进“单次读写能量”。
复位/初始化、装载、读取、保持、唤醒分开统计；未知X/Z如实报告。

| 编号 | 刺激与窗口 | 至少输出什么 |
| S0 静止保持 | 宏已正确写入；CE不访问；合法停止CLK；A/D/控制静止 | 宏漏电和保持总功率，Q/数据是否保留 |
| S1 关闭访问但时钟运行 | 同S0，CLK=100MHz；再补一组CE关闭而外部A/D翻转 | 内部、开关、漏电、总功率，接口无效翻转的额外成本 |
| S2 连续读 | 依次读地址、重复读同址；输出固定数据与约50%翻转数据分别测试 | 每次真实读的动态能量，读延迟，最小可持续读间隔 |
| S3 连续写 | 全字写，以及实际掩码写（宽字工程为9bit选通）；地址/数据约50%翻转 | 每次实际写的动态能量，写周期，掩码写是否有完整内部访问开销 |
| S4 预读＋4096拍保持 | 四宏同址读出576bit一次；此后4096拍CE关闭，Q连接真实计算负载 | 预读能量/时延、保持功率、Q是否稳定；不应出现4096次SRAM读 |
| S5 再启动 | 从S4或合法门控保持返回，选择另一地址/权重组，再预读 | 重启的额外能量、到可用数据的延迟、保持数据正确性 |

S2/S3建议各记录0%、约50%、高翻转三类数据；第一批只做50%也可以，必须注明。
S4的计算窗口正好4096个有效样本拍，即100MHz下40.96微秒；外围预读等待单独算。
S1与S0不同：CE关闭不代表宏时钟停止，更不代表只有漏电。
重复读相同地址即使Q不翻转，内部预充电/读出也可能耗能，不能记为零成本。
掩码只写9bit，并不意味着写能量按144bit全字的9/144缩小；直接测实际WEB活动。

如果目标宏明确支持保数据低功耗模式，再做S6：进入→驻留→退出→重新读取。
记录sleep/retention功率、进入/退出能量和延迟。低功耗中Q未定义时，不得继续给p-bit喂Q；
需保留本地有效输出，或等唤醒并重新读取。S0/S1不是自动等同于sleep/retention。

另外测一次“小bank接口”即可检查系统吞吐：
实际准备采用的bank数/字宽/端口，连续搬运一个4KiB cache line、一个tile，
再跑工作缓存交替读写。输出每次操作数、周期、冲突/停顿、有效带宽和分项能量。
缓存1RW端口不能同拍读写；1R1W也须按宏的同址冲突规则验证。
无需现在就生成16MiB完整SRAM网表；先用代表性宏和小bank组核验，再明确按宏数量扩展。

五、功耗怎样换成模型参数，避免重复计费

推荐第一批使用“访问动态能量＋空闲动态功率＋各状态漏电”的账本：

  单次读动态能量 = (该窗口内部功率 + 开关功率) × 窗口时间 / 实际读次数
  单次写动态能量 = (该窗口内部功率 + 开关功率) × 窗口时间 / 实际写次数
  模块总能量 = 读次数×读动态能量 + 写次数×写动态能量
             + 空闲动态功率×空闲时间 + 各状态漏电功率×各状态时间
             + 不包含在以上项中的进入/退出额外能量

这里的连续读写窗口包括相应时钟内部功耗；漏电从访问动态能量中剔除，另按时间计。
不能再把时钟运行待机总功率乘整个运行时间，又加包含同一时钟成本的读写能量。
也可以采用整段状态平均功率计费，但与上述逐访问账本只能选择一种完整口径。
若使用“访问能量超过待机的增量”口径，则才可以将同一待机基准乘整个时间；
务必明确基准状态，不能将两种口径的单次能量混填。

单位速查：
  能量pJ = 功率W × 时间ns × 1000
  能量pJ = 功率微瓦 × 时间ns / 1000
  功率1mW持续10ns = 10pJ。
  宏物理容量bytes = 深度D × 字宽W / 8；144bit物理字为18bytes。
  每有效byte成本 = 实际激活宏/字的动态能量 / 实际请求的有效bytes。

9bit符号/幅度权重、8bit外存INT8和16bit对齐存储是不同布局，要分别记账。
一次读一个宽字但仅用部分数据，能量按实际激活的宽字算，不能只按有用bits缩小。
一次mask写同理。大权重cache若存INT8、活动tile存9bit，转换/复制成本单独记录。

| 当前模型字段 | 可以怎样替换 | 必须同时保留的信息 |
| weight_macro.read_pJ_per_byte/write_pJ_per_byte | 实测动态能量结合真实宏访问粒度折算 | 宏字宽、bank、实际有效byte、全字/掩码区别 |
| weight_macro.leakage_W_per_MiB | 正常保存状态的漏电，按实际宏容量折算 | 不包含时钟运行的额外动态待机；低功耗状态另列 |
| weight_macro.load_latency_ns | 地址/请求到可用数据的接口延迟 | 同步读拍数、时钟到Q、包装寄存器及仲裁延迟 |
| weight_macro.load_bandwidth_GBs | 可持续有效吞吐，而非仅用时钟到Q倒数 | 单bank请求间隔、端口数、bank并行和R/W冲突 |
| weight_macro.area_mm2_per_MiB | 所需宏总面积/容量，外加明确的共享外围 | 宏深度/字宽及数量，不按bit密度任意缩放 |
| active_tile_hold_W/active_tile_area_mm2 | S4的活动tile驻留保持与面积 | 与大cache是否同一实体；时钟状态；一次还是64路并行 |
| resident_read_pJ_per_tile | 一次tile准备中尚未计费的本地转换/锁存/控制 | 不重复计已经由cache读取收费的同一SRAM访问 |
| scratchpad的读/写/漏电/面积 | 同样方法测实际工作缓存 | 随机流、部分和等读写活动与银行冲突，不能沿用权重静止状态 |

目前模型还没有完整的SRAM待机动态、retention、唤醒以及bank端口调度。
这些新测项应作为新字段接入，不能全塞进“leakage”或把无字段项记零。
默认16MiB/1MiB、64GB/s、20ns、2/3pJ每byte、活动tile的0.1mW/0.02mm²/50pJ，
均是待替换的架构假设，不是已有SRAM测量结果，也不保证同一物理配置能同时满足它们。

如果cache和活动保持使用同一组宽字宏，宏面积/漏电只计一次。
如果是两层真实存储，则分别计cache和本地驻留的装载/保持；本地写入或锁存不能遗漏。
现模型tile准备50pJ不能直接代表新SRAM的整组装载能量；数据返回后按实际访问/配置动作重算。

六、时间、带宽和面积：PT能给什么，还要补什么

时间：PT给已表征宏与外围的时序检查；功能模型/datasheet给同步协议和输出保持行为。
读响应延迟与连续请求间隔要分开：流水读可延迟2拍但每拍接受1次；非流水则未必。
完整通路包含宏、bank选择/控制、互连和接收寄存器；不能只测SRAM内部时钟到Q。

带宽例子：一个144bit读端口每10ns读一次，物理峰值1.8GB/s。
4个并行端口是7.2GB/s（还未扣除无效byte、协议和写冲突）。
要在100MHz达到当前假设64GB/s，至少需要向系统交付每拍640bytes；
这不是一块小单端口SRAM可以做到的，必须增加并行宽度/bank或提高频率。
相同地址/同bank访问不能享受所有bank并行的峰值。

面积：优先从LEF/GDS宏宽高取得物理面积，并与库area的单位和含义核对。
标准单元部分另统计。输出“宏数量×单宏面积＋外围cell面积”。
库面积之和不是最终die面积；宏通道、halo、布线、供电、利用率与CTS由物理实现补充。
不要只比较相同bit数而忽略可同时读出的宽度/端口，也不要把微小宽字宏面积外推成大容量宏。

七、PT报告与回传清单

分开报告：SRAM宏、ICG/时钟外围、本地保持（若有）、bank控制/选择/总线、计算核心。
第一批可以无SPEF/无CTS，但明确“布局前/理想时钟”；输出slew与负载来自哪里。
不要重复计宏内部时钟功耗与外部时钟树；CTS有结果后再加实际外部时钟成本。

至少回传以下文件/数据，不必回传厂商完整库：
- manifest：宏/网表/模型/活动文件hash、PVT、频率、slew、负载、宏数量和端口/布局。
- power：每状态内部、开关、漏电、总功率；分宏与外围；保存报告原单位。
- windows：每窗口起止、真实读/写/掩码操作数、CLK边沿、Q翻转、有效样本数、X/Z。
- timing：setup/hold、最小周期/脉宽、gating检查、约束违例和未约束路径。
- coverage：宏是否真正link到指定libcell，功耗表是否被使用，活动覆盖与默认传播情况。
- area：宏尺寸/面积、数量、总宏面积、外围面积及是否有物理布线结果。
- functionality：读写/掩码/CE保持/门控重启检查；低功耗数据保持仅在支持时验证。

建议结果表每行是“一个宏/组件＋一个状态＋一个PVT＋一个活动模式”：
component,macro_name,depth,word_bits,macro_count,corner,voltage_V,temperature_C,
frequency_MHz,state,duration_ns,read_count,write_count,mask_bits,
internal_uW,switching_uW,leakage_uW,total_uW,
read_dynamic_pJ,write_dynamic_pJ,read_latency_cycles,issue_interval_cycles,
macro_area_um2,periphery_area_um2,annotation_status,timing_status,notes

未完成或无模型的项填NA/null，不能填0。
活动覆盖要看SRAM的CLK/CE/地址/数据/掩码是否可信，不要求宏位单元内部网表展开。
如果厂商库只在某控制组合下有功耗表，就核对实际波形是否命中了对应控制状态。
分项求和必须等于整体报告；wrapper中的真实宏数量必须与面积和功耗的乘数一致。
