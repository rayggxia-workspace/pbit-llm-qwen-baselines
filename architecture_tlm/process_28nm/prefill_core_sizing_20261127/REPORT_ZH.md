# Qwen3-4B prefill的一至两秒资源预算

**后续复核：** 用户允许以INT8 Attention对照后，[文献与面积复核](LITERATURE_AND_INT8_ZH.md)显示，以下96/192核与12/48MiB状态是特定组织的未优化参考，不是28nm的最低资源要求。新复核保留原RESULTS与脚本，不将INT8/多播候选写成已完成TLM或PPA。

2026-11-27，Issue225 / PR266。模型为Qwen3-4B后训练版，36层、隐藏宽度2560、FFN宽度9728，batch=1、输入2048 token，28nm/250MHz。FFN仍用W8、GU16/Wd32，P-CIM每核K64/M128、8KiB、16个32×128bit bank；装载一块32拍，计算帧18/34拍。QKV/O保持BF16，Attention先按完整稠密因果计算估算，最后一个prompt位置执行一次LM head。

**建议把“约2秒”方案先按96个P-CIM核规划；“约1秒”按192核规划。它们分别对应约1.8秒和0.94秒的配套资源服务估算。只增加P-CIM核不能达到这个整机目标，数字矩阵、向量、部分和更新和权重复用必须同步扩容。**

## 核数从哪里来

GU每个token每层需要152个输出组×40个输入块＝6080帧；每帧同时生成64个g与64个u。Wd需要20个输出组×152个输入块＝3040帧。全部2048个token、36层合计：

- GU：448,266,240帧×18拍；
- Wd：224,133,120帧×34拍；
- 总工作量：15,689,318,400核周期，即250MHz下62.7573“单核·秒”。

因此，单看FFN计算，下界为62.7573/核数秒：

|P-CIM核数|FFN纯计算下界|
|---:|---:|
|5|12.55秒|
|32|1.96秒|
|64|0.98秒|
|96|0.65秒|
|128|0.49秒|
|192|0.33秒|

32核与64核分别只是FFN达到2秒、1秒的理想下限，不是完整prefill核数。这些核在36层之间复用，并非每层复制一份。

## 整机还需要什么

QKV/O投影共1.933万亿MAC；稠密因果QK/PV约0.619万亿MAC。按当前256路BF16 FMA、II=1及既有64拍发射＋4拍收尾代理，QKV/O约32.09秒，QK/PV约10.27秒；原16路向量的Softmax另约4.83秒。复制FFN核不会减少这些时间。

FFN还需要860.67亿次跨K标量更新。当前两路32-lane后端，即使不计SRAM等待，完成更新也至少5.38秒。这是必须随计算核扩容的另一个共享资源。归约、格式编码和随机源应按簇就近供给，避免把几十个核集中接到原两路后端。

本轮目标后端采用独立prompt行交错的“读下一状态／更新当前状态／写上一状态”流水。现有decode的state_worker仍按一次事务的读取、计算、写回顺序阻塞，不能直接把16/32个worker数字改大后声称已经实现该流水。若读取、更新、写回阶段无法重叠，按本轮相同合计带宽预算，两档服务时间约变成2.46秒和1.27秒；因此状态流水是实现1–2秒目标的明确工作项。

下面是两档具体资源预算；外存不加宽，采用100GB/s有效带宽情景，对应现有136.46GB/s峰值的约73%。数字FMA只是运算lane数量，不能把它们接到原窄操作数接口而直接继承此吞吐；需要分块GEMM的数据复用和广播供数。

|资源|约2秒候选|约1秒候选|
|---|---:|---:|
|P-CIM核数|96|192|
|共享BF16 FMA lane|16,384|32,768|
|向量lane|512|1,024|
|32-lane跨K更新worker|16|32|
|FFN编码服务副本|4|8|
|一块权重连续服务的prompt行数|128|256|
|状态SRAM读写合计吞吐预算|2,048GB/s|4,096GB/s|
|P-CIM权重容量|768KiB|1.5MiB|
|按现有64位状态直接扩展的载荷预算|12MiB|48MiB|
|服务级估计|**1.80秒**|**0.94秒**|

状态容量按“每核保留B行×128个输出的跨K状态”预算，不是已优化后的最小值。若FP24通过实际前向PPL，载荷可分别降为4.5MiB和18MiB；22位紧密打包还可略降，但本轮性能不依赖这些候选数制。输入、g/u缓冲、数字矩阵累加与Attention工作集还需另计。因此prefill不能直接沿用decode的12KiB状态容量。

两档各阶段服务时间如下，单位为秒：

|阶段|96核候选|192核候选|
|---|---:|---:|
|FFN采样/装载/状态/权重访存的较慢项|0.672|0.336|
|QKV/O|0.501|0.251|
|稠密QK/PV及Softmax|0.312|0.156|
|Norm、RoPE、残差|0.047|0.024|
|FFN尺度/概率编码|0.181|0.091|
|其他中间量外存读写|0.078|0.078|
|最终LM head|0.008|0.008|
|合计|**1.800**|**0.943**|

同一2秒配套、只把核数改为64时为2.12秒；同一1秒配套、128核时为1.10秒。96/192是留出其他阶段服务时间后的核数选择，不是简单给32/64乘一个经验系数。

## 权重必须跨token复用

prefill的prompt已知，同一层的多个位置可以并行处理。一块权重装好后，连续服务128或256个位置再换下一块；不能逐token重装全部权重，再把decode时间乘2048。

FFN全部层W8权重合计2.690GB，BF16 QKV/O权重1.887GB。若每块仅复用32行，整段要读约292.93GB矩阵权重，在100GB/s下仅此一项就需2.93秒；复用128行降为73.23GB、约0.73秒。这里没有要求全部模型权重常驻，也没有提高DRAM带宽。

96核候选对复用粒度的服务估算为：32行3.56秒、64行2.09秒、128行1.80秒、256行1.80秒。128行以后主要受部分和后端和数字计算限制；再增复用会增加状态容量，却没有相应加速。

## 如果QKV/O也改成P-CIM

若另做W8、GU16式输入采样的QKV/O，线性层总核时由62.76增至79.74单核·秒，对应2秒至少40核、1秒至少80核。此时可以减少数字投影资源，但仍要处理动态QK、Softmax/PV及编码。这是不同的量化/采样方案，当前FFN的PPL结果不覆盖它；本表保持已有BF16投影以便估算现有算法的硬件扩容需求。

## 估算层级与复算

本轮为资源选型的解析服务模型，不是已实现prefill RTL或逐bank完整TLM。阶段按数据依赖相加，阶段内计算、部分和和权重DRAM服务取较慢项；计算P-CIM装载32拍并跨多行复用。共享DMA及实际bank冲突、归约对齐、数字GEMM广播、状态映射与队列回压尚需用代表性prefill分块回放确认。当前没有新的芯片PPA、准确率或服务器任务，也未改变decode默认。

帧数与3×H×I MAC守恒、因果pair数、64位状态读写、32拍装载、模型维度和三个来源SHA均由脚本检查。源码与最小输入在本目录，可直接复算：

```text
python -B architecture_tlm/process_28nm/prefill_core_sizing_20261127/estimate.py
```

`--source-root`可指定完整项目目录，并核对原配置/合同/BINDINGS原字节SHA。`SOURCE_INPUTS.json`是最小复算输入；`RESULTS.json`和`RESULTS.sha256`封存本轮数值。当前单核价格是旧19bit表征，不据此次核数估算新增21bit整机面积/能耗。
