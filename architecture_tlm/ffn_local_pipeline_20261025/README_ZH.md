# FFN本地双缓冲：分清调度、带宽和计算瓶颈

Issue186；独立分支 `task/186-local-pipeline`；基于main `d83eeb1f`。新代码全部放在本目录；`unified_v6` 原实现、默认配置、历史结果不改。

**本轮问题不是“每拍都从SRAM重新读权重”，而是装载下一批权重、计算和恢复被串行连接。新方案让下一批权重提前装好。** 单层因果对照已显示：同样的阵列和采样数，FFN约7.52→4.97ms；之后单独翻倍SRAM带宽，仅再降低约3.5%。完整36层结果、每项配置和源SHA见 [自动汇总](RESULTS_ZH.md)。

## 1. 改了什么

旧版：DMA可预取，但下一批共享SRAM写入、本地装载要等当前计算和恢复结束；计算还与本地装载共用资源锁。

新版每次最多保留两个tile：

```
本地权重bank A：装好 → SC采样计算 → 系数恢复/部分和累加 → 释放
本地权重bank B：       DMA → shared填入/读出 → 装好 → 等待计算
SC阵列/时间计数器：    只有一套，下一计算仍等待上一恢复完成
```

- 同一输出块、同一输入窗口内：下一bank装载可以覆盖当前计算/恢复。
- 跨输出块或输入窗口：只提前DMA，shared访问仍等部分和写回和新窗口读取，保留因果与bank竞争，避免“先预约未来访问、阻塞更早就绪访问”的错误。
- 每个bank有独立权重、系数和所有权；权重/系数回包分别有有限容量。释放要等恢复完成，不在阵列计算结束时提前覆盖系数。
- 系数也提前通过同一个DRAM actor读回。`layer_serial_new`关闭装载重叠，单独显示这个变化；不能把它与双缓冲收益混称。
- 可选 `weight_bypass`：完整DMA响应收到后直接搬入本地bank，跳过shared SRAM写入和重读。仍付DMA响应缓冲、本地搬运时间和相应活动；不是零缓冲逐beat直达。
- 不改变W8、K64量化边界、四档输入、采样数、逐K64恢复/舍入/累加顺序。GU=64；主对照NL/Wd=64；128单独扫描。计数保持精确，没有引入OR近似。

主对照资源相同：100MHz核心；8×64×64 SC阵列；R8；8MiB shared SRAM、64bank/64GB/s、55nm SS F宏80MHz；标准HBM2时序8通道/16GiB/理论256GB/s。新增32KiB本地权重bank及32B系数bank，SC阵列、计数器、归约器和4KiB宽部分和不复制。两个bank的选择/驱动/连线和供数时序还需要物理实现表征，不当免费面积。

## 2. 用单因素扫描找瓶颈

下表全部为同一层的FFN时间（包括输入/非线性编码、最终转换和FFN残差），不是整机估算。实际数据来自Slurm3074，非凭经验填数。

| 改动 | FFN ms/层 | 解读 |
|---|---:|---|
| 原先R8调度 | 7.5212 | 原参考 |
| 只提前系数DMA，关闭本地重叠 | 7.2718 | 先消除部分供数等待 |
| 两个本地bank重叠装载 | 4.9657 | 比原参考少34.0%，仍搬同样的shared字节 |
| 再绕过shared权重中转 | 4.7397 | 再少4.6%；减少流量主要利于SRAM动态能量 |
| 在双bank上将shared带宽翻倍 | 4.7940 | 仅再少3.5%；并非当前FFN首要瓶颈 |
| 系数恢复16→64路、宽累加32→128路 | 4.3884 | 再少11.6%；桶移位归约仍64路 |
| SC阵列8→16个 | 3.9473 | 再少20.5%；计算、计数和对应状态增加，非同面积 |
| 部分和R8→全K | 4.6410 | 再少6.5%；要增加输入码/随机检查点窗口 |
| NL/Wd采样64→128 | 5.9382 | 增加19.6%；不能说更多采样没有时间代价 |

双bank参考中，一层阵列采样服务2.166ms，桶移位归约＋系数恢复1.8012ms，宽累加约0.3880ms。这三项在本版仍按波串行，合计约4.355ms，已经占4.966ms的87.7%。局部装载带宽再大也不能消掉这些计算时间；若要进一步重叠计算与恢复，需要有限的计数结果快照/双计数bank，不能直接删除依赖。

**结论限定在当前参数附近：先修调度，再优先扩计算及恢复吞吐。** 带宽翻倍是64→128bank、64→128GB/s，本地接收也1024→2048B/核心拍；容量、F宏个数与频率不变，但新互连/端口不是无成本。它不是“只改一行带宽就证明电路能达到”。

注意：单层总时间中lm_head很大，shared带宽翻倍对lm_head和普通投影帮助显著。必须分FFN与其他部分，不能从FFN仅3.5%推断整机不受SRAM约束。也不能将资源busy时间直接相加：部分装载已被计算覆盖；主依据是控制变量后的相位时延差。

## 3. 每读一次，到底做几次计算

| 数据 | 当前读取/保持方式 | 一次装入后的使用 | 是否还应放寄存器/局部状态 |
|---|---|---|---|
| W8权重 | 每层每权重从DRAM读一次；shared路径写一次再读一次，随后本地保持 | 64次采样事件，最终形成一个近似乘积；T128则128次 | 已本地驻留。再增加权重缓存不自动提高有效乘积复用；第二bank主要隐藏下一批装载 |
| 输入x的P8码 | 每K64编码一次；R8输入窗口读入本地，跨输出波重用 | 一波最多512个输出；GU共38个输出波 | 保存码、尺度与重放状态合理；不存64份随机流 |
| g/sigmoid(g)/u码 | 非线性编码一次后保留；现场生成三流AND，直接进Wd | Wd共5个输出波，重放对应随机帧 | 局部码/随机状态有用；不额外生成连续z缓存 |
| 时间计数器 | 每帧本地更新，帧末输出 | 同一计数器累计T次事件 | 已经是本地状态，不会每拍读写shared SRAM |
| 跨K64的宽部分和 | 512×64bit＝4KiB；R8合并后才写shared | 每次写回前合并8个K64结果 | 可以扩大驻留窗口，但需要同步扩大码/检查点窗口，不能只算4KiB |

一个FFN有71.25MiB W8权重；8×64阵列每波32KiB，共2280波。不是2280次重复读取相同权重，而是不同tile覆盖全矩阵。B1 decode中数字与SC的“有效乘积/每次权重装入”都为1；64个随机事件不是64个有效MAC。

shared权重中转每层142.5MiB（不含系数）；部分和R8读写2.059MiB，R1为17.645MiB，全K为0.168MiB。因此本轮双缓冲提速主要来自重叠；bypass才真正减少权重中转字节。不要把部分和88%的流量下降说成FFN88%的加速。

当前装载的是完整、对齐的权重tile，权重有效字节占比并不低。单层双bank时，shared权重＋系数中转约149.568MB，摊到FFN时间约30.1GB/s，低于64GB/s接口；这主要是计算阶段限制了持续需求，不应直接叫做“SRAM本身太慢”。单次搬运的端口速率、整个阶段的平均流量和有用计算复用是三种不同指标。

可逐批核查[16波时间线CSV](TIMELINE_EXCERPT.csv)和[带原件SHA的JSON](TIMELINE_EXCERPT.json)：DMA、program、compute和retire分别列出；没有把64次采样直接写成64个无条件整机周期。

数字基线的 `digital_local_activation_read_byte` 是MAC输入消费数，没有展开广播后的物理RF读数。这里不据此虚构RF/SRAM能量；正式比较应分别记录操作数使用、物理读、扇出。

## 4. 成熟模拟器为什么更快

[独立源码核查](SIMULATOR_COMPARISON_ZH.md) 给出固定commit、官方链接和已有原生probe。

- ONNXim/Gemmini常见组织：load/execute/store解耦、双缓冲、输入广播、accumulator保留部分和。新版本借鉴这些机制，并保留有限容量和回压。
- LLMCompass普通tile路径也计输入复用、部分和驻留与双缓冲。但B1 GEMV快捷路径直接取“计算与DRAM时间的最大值”，不展开L2供数。它较快的一部分是更乐观的模型边界，不是权重被神奇地多用了几次。
- GPU级资源配置还远大于本轮100MHz小阵列。不能拿A100配置的数字与小型55nm条件的结果直接说明调度好坏。

本轮没有声称完整Qwen已移植ONNXim。旧原生四tile测试只用于检查并行/依赖机制；完整结果仍来自我们的事件TLM＋DRAMSys。

## 5. 能量、面积和时间的证据边界

- 时间：真实DRAMSys地址访问/队列/标准HBM时序，校准SRAM读写；计算/恢复/本地权重端口仍是有界宏合同。完整36层合成事务执行，未运行模型权重。
- 双缓冲shared：访问字节不变，所以已校准SRAM内部动态能量不变；完成更快可减少漏电/等待能量，但新增bank和驱动成本尚未知。
- bypass：每层少149,568,000B shared访问（权重＋系数的写/读），可据校准宏计算SRAM内部动态节省；不得等同整机能耗。HBM公开电流占位为0，模型明确禁用其能耗，0不代表真实DRAM免费。
- 面积：新增32KiB权重、32B系数、bank控制/选择端口需要单独标定。没有扩大SC阵列/计数器，不把容量当测得面积，也不假定完全CIM接口已签核。
- 数值：保持逻辑K64与随机帧顺序；FFN真实随机端点仍是有界宏，按墙钟重播种可能随调度变化，不能宣称逐bit相同。GU固定点恢复宏和新路径PPL仍待闭环。
