当前INT8/概率码与BF16接口的转换开销核对
2026-10-16

后续更新：独立转换及累加比较RTL已实现并完成功能验证，见
../format_conversion_rtl_20261016/README_ZH.txt。
下文是实现前的TLM预算审计；其中“未新增转换器”描述该次审计当时状态。
当前仍未运行用户工艺库DC/PT，不能把下文通用预算改称转换器实测功耗或面积。

结论
====
现有TLM没有独立标定的BF16转换器，无法给出可信的专属面积mm²或实测pJ/次。
已经计入相关工作的两个通用预算是input_encode_vector_ops=6，
finalize_vector_ops_per_partial=2。它们混合了编码、尺度恢复和部分和处理。
按照旧存储成本情景，这两项逻辑和通用向量接口能量合计0.116987904mJ/token，
约占该情景整机174.655910943mJ/token的0.06698%。这不是转换器的测量值或上界。
不能再在原总能量上加一次此金额；它原已存在于digital_vector和scratch_access。

一、当前实际格式与路径
=====================
以Qwen2.5-0.5B、24层、h=896、m=4864、64输入分块的FFN为范围。
固定INT8权重、8bit输入阈值、4096次采样、group64共享输入随机字。
不将Attention中Ising偏置编码混入本次FFN格式转换账目。

原始权重：BF16 → 离线INT8 code、符号/幅度存储形式和tile scale。
这是模型准备动作，不按每个token重复量化；加载这些已准备数据仍有存储/传输费用。
固定的scale和T归一化系数可以离线准备，但运行时将新的累加结果乘相应系数仍需算。

运行时：
  x连续值 → 8bit幅度阈值＋符号 → 随机矩阵gu → 宽累加/尺度恢复得到g、u
  → 连续SiLU(g)u → 8bit幅度阈值＋符号 → 随机矩阵down
  → 宽累加/尺度恢复 → BF16 y → 残差相加。

注意：A8是8bit无符号概率阈值加一个符号位，不等同于标准8bit有符号INT8激活。
INT8权重乘法结果也不是INT8：计数/点积/跨块累加需要更宽整数或参考浮点累加。
软件参考使用x.float()和FP32中间结果，最后y.to(x.dtype)回BF16；这些软件转换
不是已实现的硬件流水。g/u硬件使用BF16还是FP32仍需指定，不能把转换成本混为一种。

二、运行时每token的逻辑数量
==========================
x编码到8bit阈值：                 24×896             = 21,504个
z=SiLU(g)u编码到8bit阈值：         24×4864            = 116,736个
编码合计：                       24×(896+4864)      = 138,240个
gu宽累加结果恢复为连续值：         24×2×4864          = 233,472个
down最终结果恢复并输出：           24×896             = 21,504个
最终逻辑矩阵输出合计：            24×(2×4864+896)    = 254,976个

gate/up共用相同输入编码，融合gu时不重复量化x。
输入概率阈值在4096拍间保持，并跨输出组复用，不是每拍/每乘法重新做BF16量化。
以上254,976是每层完整投影的逻辑输出数，不等于当前实现中所有部分和恢复次数。

当前按64输入分块得到的标量部分结果数：
  每层gu：14×9728=136,192；每层down：76×896=68,096。
  24层合计4,902,912个部分结果，等于TLM sc_tile_frames×64。
每部分结果目前预算2个通用vector op，包括尺度对齐/累加；不全是INT8↔BF16转换。
若采用不同块尺度，恢复/对齐不能自动省略；若能用可验证的宽定点跨块累加、最后
统一转换，可减少浮点往返，但需要保证尺度和累加精度并重新验证质量。

三、目前TLM已经记入的广义预算
===========================
旧占位存储单价：vector op=1pJ；每op通用接口4byte；读/写各2/3pJ每byte。
因此每op逻辑1pJ、平均接口10pJ。通用接口是模型假设，不代表转换电路一定落SRAM。

项                         操作数量       逻辑uJ/token   接口uJ/token   合计uJ/token
输入编码（每值6op）         829,440        0.829440       8.294400       9.123840
部分和后处理（每部分2op）   9,805,824      9.805824       98.058240      107.864064
合计                       10,635,264     10.635264      106.352640     116.987904

按64 vector op/cycle、100MHz预算，对应通用向量服务时间1.66176ms/token。
这是所需服务工作量，不是实测转换器延迟，也不应简单从总时间中扣掉作为实际加速。
独立的部分和缓存读写另有账目，本表未把它们全部归为数制转换。
SiLU/分支乘法、PRNG、比较器/阈值保持已在其他项中，不混进这里重复计费。

启用现有CACTI cache/scratch成本对照时，可用audit_format_conversion.py重新归因；
仍然只是成本假设下的预算，不会因此获得转换器的真实55nm功耗。
这些比例只对应当前476ms级、T4096的整机情景。缩短T、减少SC核心能耗后，
固定转换费用的占比可能上升，不能推广为所有架构都小于0.1%。

四、转换器实际需要哪些电路
=========================
BF16/FP32 → A8阈值：符号与指数/尾数处理、按固定scale缩放、移位、舍入、饱和。
现有Sx/Sz为校准后固定2的幂，缩放可用指数偏移/移位实现，不必每token求最大值
或做一般浮点除法。需要定义与参考一致的round-to-nearest-ties-to-even和clip。

宽定点/整数 → 连续值：符号/幅度、前导零检测、规格化、尺度恢复、舍入与指数构造。
INT8→BF16的纯转换与宽累加器→BF16不是同一个电路；后者不能按8bit转换成本估算。
权重tile scale未必是2的幂，运行时结果恢复可能含尺度乘法；离线存好scale不能
让乘以运行时累加值的动作消失。可以离线合并系数，再针对选定数据通路实现。

面积按同时工作的转换通道和复用方式计算，与每token转换次数不同。
例如一个共享输入编码模块可串行写入64个阈值槽；不是每个乘法单元复制一个转换器。
也不能因为有8个SC阵列就默认必须复制8套完全相同的输入转换器。
当前TLM的digital.area_mm2=1是整个数字模块占位，不能据此拆出转换器面积或百分比。

五、补齐实测成本的最小方案
=========================
针对现有格式先独立实现并标定三类动作：
  1. BF16→A8阈值＋符号（固定2的幂scale）。
  2. 宽累加结果→BF16或FP32（包括实际选定的尺度恢复），并区分部分和对齐。
  3. FP32 z→A8阈值（若保留当前软件参考的FP32 SwiGLU路径）。
各给出：输入/输出位宽、舍入/饱和、scale类型、pipeline latency、issue interval、
单lane面积、idle/active功耗、每值动态能量与真实活动条件。
先标定单lane或小lane组，按真实需求决定复用/复制，接口缓冲另列。
有这些数据后替换旧6op/2op相应的功能预算，不直接叠加新转换器成本。
这只是下一步建议，本次未新增/综合转换器，也未声称已测得面积。
